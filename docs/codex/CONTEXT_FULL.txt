2. CODE QUALITY / READABILITY RULES
========================================================================

GENERAL
-------
- Readability is more important than micro-optimization unless performance is genuinely material.
- Code should be understandable by someone who knows very little about the repo.
- Prefer straightforward code over clever one-liners or compressed logic.
- A person new to the project should be able to follow the main flow from top to bottom without jumping through many files.

FILES
-----
- One file should have a clear responsibility.
- Avoid giant files that contain several unrelated concepts.
- Also avoid artificial fragmentation.
- A main file is allowed to be reasonably long when it contains real service orchestration.
- Do NOT create a *_application.cpp + *_application.h pair just to move the same main logic out of main().
- Separate a component only when it has a meaningful responsibility, reuse, lifecycle, state, or abstraction boundary.
- Several small tightly-related types may live together.
- A class does not automatically need one header + one cpp if that causes noise.
- Likewise, a whole subsystem should not be jammed into two enormous files.
- A large component can reasonably be a .h for interface/state and a .cpp for implementation.

FUNCTIONS
---------
- Functions should do one understandable job.
- Names should explain intent.
- Avoid vague names such as calc(), process(), handle(), doStuff() when a more specific name is possible.
- Avoid huge functions when they clearly contain several independent steps.
- Also avoid extracting trivial one-line functions purely to reduce line count.
- Main flows should read almost like pseudocode.

ENTRYPOINTS
-----------
- main() should be understandable.
- It may contain service-level orchestration directly.
- It should not contain deep reusable domain algorithms.
- Do not reduce main() to a one-line wrapper unless the abstraction genuinely provides value.

COMMENTS
--------
- Comments must be in English.
- Comments should explain WHY something exists or what invariant/timing rule is important.
- Do not write comments that simply restate the next line.
- Important trading timing/economic rules should be documented close to the code.

LOGS
----
- Logs must be in English.
- Logs should be concise but include useful context when relevant:
  symbol, orderId, tradeId, side, quantity, price, reason, timestamp.
- DEBUG for detailed diagnostics.
- INFO for meaningful service/trading events.
- WARN for recoverable abnormal states.
- ERROR for real failures.
- Do not log secrets.

STRUCTURE
---------
- Separate domain logic from infrastructure where possible.
- Strategy should not care about dashboard rendering.
- Risk should not know how JSON is drawn.
- Portfolio should not depend directly on Hyperliquid-specific details.
- Prefer small explicit interfaces between modules.
- Avoid mutable global state.
- Ownership in C++ should be obvious.
- Prefer named domain structs over long lists of ambiguous doubles.
- Avoid magic numbers.
- Prefer one source of truth for PnL, equity, sizing, fills, etc.

TRADING-SPECIFIC
----------------
- No hidden look-ahead.
- Timing rules must be explicit.
- Backtest and live should share economic logic where reasonable.
- Differences between replay/backtest/live must be deliberate and documented.
- Important invariants should be checked.
- Duplicate signals/orders/fills must be easy to investigate.
- Risk, sizing, fills, reconciliation, positions, PnL and order state should be easy to trace.

BUILD / REPO HYGIENE
--------------------
- The supported project should compile with the normal build.
- No old.cpp / final2.cpp / tmp.cpp naming.
- Remove one-off migration scripts after their job is finished.
- Generated outputs should live in dedicated output/run directories.
- Avoid dozens of historical Markdown notes in active folders.
- Current docs should describe current behavior, not narrate development history.

38. LIB REFACTOR DESIGN PRINCIPLE
========================================================================

The large header splits performed in PASS 2A..2H are NOT a command to convert
every header into a header/cpp pair.

Use judgment.

Split when:
- the header contains hundreds of lines of non-template implementation,
- moving implementation makes the public contract substantially easier to read,
- compile/build wiring remains clear,
- the component still remains cohesive.

Do not split when:
- implementation is template-dependent,
- the file is already a small cohesive value type,
- the result would create a tiny cpp containing trivial getters,
- a coherent codec/contract implementation would become scattered across many files.

The user strongly prefers a practical middle ground.
